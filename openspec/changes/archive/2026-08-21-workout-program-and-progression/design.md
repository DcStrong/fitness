## Context

Уже есть: библиотека упражнений, шаблон тренировки (`kind=template` + nested sets), copy-on-assign (`kind=student_copy`), одно `sessions.student_plan_id`, страница занятия, recurring booking (ПН/ЧТ/СБ 13:00) и (в соседнем change) логи подходов при complete.

Дыра: персонализация и календарь не связаны. Тренер правит веса внутри упражнения, вешает максимум одну тренировку на слот и не может сказать системе «на ПН/СБ жим, в ЧТ ноги, через две недели +5 кг» так, чтобы будущие сессии заполнились сами.

Стейкхолдер — тренер. Ученик читает состав занятия и копии, не редактирует программу.

## Goals / Non-Goals

**Goals:**

- Чёткие слои: упражнение (база) → шаблон (рецепт) → копия ученика (персональные веса) → программа серии (что в какой день) → снапшот на сессии (факт плана на дату).
- Несколько тренировок на одно занятие.
- Таблица нагрузок на уровне тренировки (UI + один PATCH весов).
- Единый экран программы по weekday серии с горизонтом и целью прогрессии.
- Материализация на booked-сессии; rolling, если complete по плану; hold при промахе.

**Non-Goals:** web, лог ученика, RPE/1RM, прогрессия по reps/объёму, несколько программ на одну серию, live-sync шаблона в копии.

## Decisions

### 1. Слои данных — копия + снапшот, не overlay на каталоге

| Слой | Что хранит | Кто меняет |
|---|---|---|
| Exercise | name, kind, tags | тренер в библиотеке |
| Template | состав + дефолтные сеты | тренер, все ученики не затрагиваются |
| Student copy | персональный состав/веса | тренер для одного ученика |
| Program | weekday → список template ids, rules прогрессии, horizon | тренер для пары coach–student + серии |
| Session items + prescription snapshot | что делать **в эту дату** | система при apply; тренер override |

Альтернатива «одна живая копия, сессии всегда читают её» отвергнута: правка «на сегодня» ломает всю прогрессию. Альтернатива «дельта-overlay на шаблоне» отвергнута — уже выбран copy-on-assign.

Персональные кг **не** пишутся в `exercises`. Библиотека остаётся базовой.

### 2. Несколько тренировок на сессию

Таблица `session_workout_items`: `(session_id, sort_order, student_plan_id, source, override_at)`.

- `source`: `program` | `manual`.
- GET session: `workouts: [{ studentPlanId, title, goal, exercises, source, overridden }]`.
- `studentPlanId` на `sessions` **сохраняется** как первый item (back-compat). PATCH одного id по-прежнему заменяет список одним элементом.
- Новый PATCH `{ workoutPlanIds: uuid[] }` (ordered, 0 = detach all). Каждый id — `student_copy` этого ученика; template id клиент резолвит assign-ом, как сейчас.

Complete без логов копирует **снапшот сессии**, не текущую копию (иначе прогрессия «уедет» в логи).

### 3. Таблица нагрузок — UI, плюс узкий API

Не новая доменная сущность. Экран шаблона/копии: секция «Нагрузки» — плоская таблица exercise × вес (одно поле на упражнение `weight_reps`, применяется ко всем сетам этого упражнения). Состав (какие упражнения, reps, rest) редактируется как сейчас, но не обязателен для смены кг.

`PATCH /plans/:id/loads` `{ items: [{ exerciseId, weightKg }] }` — owner coach; plan `template` или `student_copy`; неизвестный exerciseId → 400; `bodyweight_reps`/`duration` игнорируются или 400.

Альтернатива «только nested PATCH exercises» — оставить как есть для состава; loads — чтобы клиент не собирал полный список сетов.

### 4. Программа привязана к RecurringBooking

Одна `workout_programs` на `recurring_booking_id` UNIQUE. Weekdays программы ⊆ weekdays серии. Item: template → идемпотентный assign в `student_copy`, в item хранятся оба id.

Нет серии — нет автоматериализации по дням недели. Разовое занятие: несколько тренировок вручную с календаря/страницы сессии (без прогрессии по weekday).

Альтернатива «программа на CoachStudentLink без серии» — позже; для заявленного сценария «ходит ПН/ЧТ/СБ» серия уже есть.

API (черновик):

- `PUT /recurring-bookings/:id/program` — upsert days + items + progression rules + `horizonWeeks` (1–8, default 2). Транзакция. Сразу `apply` на горизонт.
- `GET /recurring-bookings/:id/program` — days, items с titles, preview весов по ближайшим датам, rules.
- `POST /recurring-bookings/:id/program/apply` — пересчитать снапшоты будущих booked-сессий серии в горизонте. Query/body `force?: boolean` (по умолчанию не трогает `override_at` и completed).

Permissions: `sessions:book_for_student` + owner серии; чтение как у recurring GET. Студент GET программы MAY (read-only), без PUT.

### 5. Прогрессия — цель на горизонт, линейная по вхождениям

Rule: `(program_id, exercise_id)` → `startWeightKg`, `deltaKg`, `incrementKg` (default 2.5), `holdOnMiss` (default true).

Старт: явное `startWeightKg`, иначе max вес этого упражнения на student_copy (по всем дням, где оно есть), иначе последний completed log пары, иначе 0 (не материализовать кг — оставить как в копии).

Алгоритм apply для упражнения E:

1. Собрать будущие (и сегодняшние booked) сессии серии в окне `horizonWeeks`, у которых в program-day есть тренировка с E, сортировка по `startsAt`.
2. Пусть `n` точек, индекс `i = 0..n-1`.  
   `raw = start + delta * (n == 1 ? 1 : i / (n - 1))`  
   `weight = round_to_nearest(raw, incrementKg)` (последняя точка MUST быть start+delta после округления ближайшим шагом; при конфликте приоритет у конечной цели).
3. Записать вес во **все сеты** этого упражнения в **снапшоте сессии**. Копию ученика не переписывать на каждую дату (копия = «базовый персональный рецепт»; даты живут в снапшотах). Опционально синхронизировать копию на `start` при первом apply — чтобы хаб/список копий не врали; **решение: копия хранит start (текущий рабочий вес), снапшоты — кривую.** После успешного rolling обновлять копию до нового start.

Preview в GET program: массив `{ date, weekday, exerciseId, weightKg }` для UI «через две недели жим 85».

Альтернативы:

- «+X кг каждую неделю» без цели — хуже для формулировки пользователя.
- «+X каждый раз, когда есть упражнение» — слишком агрессивно на ПН+СБ (два скачка в неделю).
- Процент 1RM — non-goal.

### 6. Rolling vs hold — тренер не вмешивается, если всё по плану

После `complete` сессии, принадлежащей серии с программой:

- Для каждого E из снапшота: `actualMax >= prescribed - 0` (допуск 0 кг в v1; равенство или больше = успех).
- Если **все** правила с `holdOnMiss` успешны на этой сессии (или упражнение не выполнялось — не считается промахом, если его не было в снапшоте): ничего не делать до края горизонта; когда до конца горизонта остаётся < 1 неделя, **авто-apply** сдвигает окно: новый `startWeightKg = last successful prescribed/actual max`, тот же `deltaKg` и `horizonWeeks` (повторить кривую). Копия обновляется до нового start.
- Если промах по E: `hold` — будущие снапшоты E в горизонте переписать на `actualMax` (не ниже last good), **не** продолжать delta, пока тренер не снимет hold (поле rule или «Продолжить прогрессию» = apply с пересчётом start от актуального). Другие упражнения не стопаются.
- Сессии с `override_at` не пересчитываются, пока тренер не снимет override («Вернуть по программе»).

Альтернатива «тренер жмёт Apply каждую неделю» — противоречит «не заходить в каждую тренировку». Авто-apply только на complete+success и на sync серии (новые слоты получают программу).

Recurring sync: после создания новых booked sessions вызвать тот же apply (без force).

### 7. Flutter — один экран «Программа», обман UI для весов

Маршрут `/recurring/:id/program` (тренер). Входы:

- деталь серии: «Программа»;
- хаб ученика / календарь booked слота этой серии: «Программа на неделю».

Экран (один скролл, без wizard):

1. Шапка: ученик, ПН/ЧТ/СБ 13:00, горизонт (степпер 1–2 по умолчанию, до 8).
2. Секции по weekday: карточки тренировок, «Добавить» из своих шаблонов (assign+привязка). Несколько карточек = несколько тренировок в этот день.
3. У каждой карточки — свёрнутая таблица нагрузок (те же кг, что PATCH loads **на копии** как start; превью кривой мелким текстом).
4. Блок «Прогрессия»: автосписок уникальных `weight_reps` из программы; поле «сейчас» и «+ кг за горизонт». Пустой delta = без прогрессии.
5. Превью ближайших дат. CTA «Сохранить» = PUT + apply.

Календарь: subtitle слота через запятую названия тренировок.

Страница занятия: стек секций по `workouts`; «Добавить тренировку»; правка веса на сессии ставит override. Не ходить в библиотеку упражнений за персональными кг.

Редактор шаблона: секция «Нагрузки» над/под списком упражнений (не аккордеон сетов).

Bloc/Cubit only, папка `features/workout_program/`.

### 8. Permissions и модули

Новых permission codes нет: программа — часть recurring booking. Loads — `plans:update_own`. Session multi-attach — как сейчас `sessions:book_for_student`.

Nest: модуль `workout-programs` рядом с recurring; apply-сервис используется из complete (hook) и sync. Не считать веса в Flutter.

## Risks / Trade-offs

- [Округление не попадает в точный +5] → шаг 2.5; последняя точка якорится на start+delta.
- [Тренер правил копию, apply затёр сессии] → снапшот сессии независим; apply без force не трогает override; копия = start, не каждая дата.
- [Две тренировки с одним упражнением в один день] → одно вхождение E на сессию (max веса из items или сумма сетов обоих — **решение: объединять сеты по порядку, прогрессия по max рабочему весу дня**).
- [Нет логов complete] → rolling не стартует; apply всё равно заполняет горизонт от start. Зависимость от `workout-progress-and-student-hub` для hold/rolling.
- [studentPlanId vs workouts] → клиенты v1 видят первую тренировку; Flutter этого change переходит на массив.
- [Часовой пояс серии] → даты вхождений в TZ серии, как materialization recurring.

## Migration Plan

1. Таблицы program / program_days / day_items / progression_rules / session_workout_items / session_prescription_sets.
2. Backfill: если `sessions.student_plan_id` NOT NULL → один item `source=manual`, snapshot из текущих plan sets.
3. Trigger/app-level: при смене items обновлять `sessions.student_plan_id`.
4. API PUT program, PATCH loads, GET session.workouts, hook complete + recurring sync.
5. Flutter экраны.
6. Rollback: дроп новых таблиц; колонка `student_plan_id` остаётся источником истины для старых клиентов.
